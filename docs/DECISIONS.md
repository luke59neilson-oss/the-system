- D18 · 2026-10-21 · TypeScript pinned to 6.0.x, not 7.x. · typescript-eslint 8.72 supports TS < 6.1; TS 7 (native port) would break type-aware linting.
- D19 · 2026-10-21 · The server serves the app shell only for GET/HEAD browser navigations (Accept: text/html) outside `/api`, `/health`, `/ws`. · Keeps missing assets and server routes as real 404s while allowing dotted client routes.
- D20 · 2026-10-21 · Banned patterns are enforced twice: ESLint rules (incl. engine purity: no host globals, clock, RNG, dynamic or non-relative imports except zod) and a repo-wide regex scanner in `npm run check`. · Inline lint-disable comments can't be reported by ESLint alone; two layers make accidental bypass unlikely.
- D21 · 2026-10-21 · `campaign.levelCap` must equal some grade's top level; grades above the cap may be defined ahead of time and are unreachable. · Keeps every reachable grade complete and lets S-grade be added by appending a grade and raising the cap.
- D22 · 2026-10-21 · Rules-config edit events (M4.9) will address array entries (grades, pools, stats, rarities, slots) by id, never by index. · An append-only log must survive inserts and reorders.
- D23 · 2026-10-21 · The rules config is strict: unknown keys are errors, so adding a setting means bumping `configVersion` and adding a migration that fills the default. · Prevents GM edits on mistyped or stale keys from being silently dropped.
- D24 · 2026-10-21 · World Stability starts at 100 (range 0–100), hidden from players by default. · DESIGN gives the range and toggle but no starting value; a dying world counts down.
- D25 · 2026-10-21 · Character state stores the grade by id, carries a `schemaVersion`, and is plain readonly data; pools are whole numbers (floored), current pools clamp to 0..max. · Survives grade inserts and replays cleanly under event sourcing (M1.3).
- D26 · 2026-10-21 · Starting class skills must be at or below the first grade's rarity ceiling and unique by name (case-insensitive, including Identify). · DESIGN §3 gives G-grade a Rare ceiling; duplicate names would make skill references ambiguous.
- D27 · 2026-10-21 · Undo is an `event.undone` event naming its target; state is the fold of every event not undone ("as if it never happened"). Undoing an undo and undoing `campaign.created` are rejected; to redo, the GM re-issues the command. · One rule covers every event type, including non-latest undo, without hand-written inverses that could drift from the reducer.
- D28 · 2026-10-21 · Replay checks undo targets against the log, then folds the events that still count once (O(n)). It does not re-check each undo's intermediate fold or reducer-validate events that were later undone, so a hand-edited log can load where appends would have refused it; logs written through `appendEvent` replay to exactly the appended state. · Keeps 50,000-event loads fast (M11.3); logs are only written through `appendEvent`, which does the full check.
- D29 · 2026-10-21 · Golden logs (`packages/engine/test/golden/*.jsonl` + `.state.json`) are frozen; payload changes need a `schemaVersion` bump and an upcaster, and a coverage test lists event types no golden log contains yet (only `character.professionGranted`, unreachable until M1.10). · Proves old campaign logs keep loading.
- D30 · 2026-10-21 · Character create events store the creation input, not the resulting character; the reducer re-derives it with the rules in the log. · Smaller events; the golden test catches any drift in creation rules.
- D31 · 2026-10-21 · A GM pool set outside 0..max is rejected, not clamped; stat changes still clamp current pools to the new maximum. · Clamping let a non-latest undo silently change what a later event meant; rejecting turns that into a refused undo (review M1.3).
- D32 · 2026-10-21 · `execute` checks command shape and authority before building events: GM and system may issue every current command; players only commands in `PLAYER_COMMANDS` (empty until M1.5) and only for their own character. · One gate in the engine that the server (M2.2) and every later item reuse.
- D33 · 2026-10-21 · Two upcaster layers: payload upcasters per type and version, and log-level raw upcasters (rename a type, split an event, change the envelope) that may never drop an event. · Covers schema changes a 1:1 payload map cannot, without editing stored logs.
- D34 · 2026-10-21 · Kept D30 (events store inputs; the reducer re-derives with the log's own rules) after review. Rules never change silently: they live in `campaign.created` until rules-edit events (M4.9). A code change to how an existing event applies must bump that event's `schemaVersion`, and its upcaster pins the old meaning. · Storing derived results in every event (levels, spreads, pools) would double the validation surface; golden logs catch drift.
- D35 · 2026-10-21 · Class spread is split cumulatively by a highest-deficit rule: each point goes to the stat furthest below its weighted share of all spread received so far (ties to stat order). This deliberately departs from ROADMAP's "largest remainder" for spread (XP shares still use largest remainder): a per-level largest-remainder split rounds the same way every level, so with 4 points over 9 equal stats Strength–Vitality would get every point. Totals sum exactly per level and every stat stays within about one point of its share (worst seen in review: 1.04); the rule can differ from largest remainder on a single level (pinned in tests). Characters store integer class weights (0–1000, equal when omitted) and spread totals; reshaping the weights (M1.10) resets the totals. · Fair long-run spread without per-level rounding bias.
- D36 · 2026-10-21 · XP shares (largest remainder, ties to the earlier participant) sum to the award; the above-level bonus is extra XP on top of a share, measured against the character's race level and derived when the event applies. The award event stores the shares and enemy level, not the level-ups. · DESIGN §5 makes the GM's split the input; level-ups follow from the rules.
- D37 · 2026-10-21 · A golden `.jsonl` never changes. Its `.state.json` may be regenerated only with a state `schemaVersion` bump, and the diff must be additive (reviewed in the commit). Character state and campaign state are now v2 (class weights, spread totals). · The log is the contract; the expected state shape is allowed to grow.
- D38 · 2026-10-21 · Free-point batches are addressed by race level (race level never falls, so it is unique). Players assign their own batches (`freePoints.assign`, the first player command); a batch must be assigned in full and then locks. Only the GM overrides (`freePoints.override`): a new full allocation stays locked, `null` unassigns and unlocks. Overrides that push a stat below 0, and unassigning a batch that is not assigned, are rejected; pools re-clamp. An override is the GM's final say: undoing an earlier player assignment leaves a later override in force. Player authority is checked on every event entering the log (append and replay), not only in `execute`. Accounting is by delta: after a GM `setStats`, an override subtracts the batch's recorded allocation from whatever the stat now is, so if a GM edit took a stat below that batch's points, the batch can't be overridden or unassigned until that edit is undone. · DESIGN §4 "assigned once, then locked; the GM can override", with every change an undoable event.
- D39 · 2026-10-21 · Party members see other characters' pools as whole-percent bars (1–99 unless empty or full), never raw current/max values; the owner sees raw values. · D5 says "pool bars"; raw maxima would reveal others' Vitality, Wisdom and Endurance (pool = 10 × stat). Raised as Q11.
- D40 · 2026-10-21 · The player projection (`projectForPlayer`) is an allowlist: every output field is copied by name, and visibility tables typed as `Record<keyof Character | keyof CampaignState, …>` force each new state field to be classified; a canary test over 1,000 random states (seed 20261022) checks GM-only and other players' values never appear. Players get a display-only rules subset (no stability, tuning or GM settings). Identify resolution is a pure helper returning only the viewer's best tier text. · New fields stay GM-only until someone deliberately exposes them; every later feature extends the projection and its canaries.
- D41 · 2026-10-21 · Unknown viewer ids make the projection throw instead of returning a reduced view. · A stale or forged client must never fall back to more (or GM) data.
- D42 · 2026-10-21 · Persistence layout: `<dataDir>/campaigns/<id>/` holds `events.jsonl` (fsynced per append), `snapshot.json` (atomic cache every 100 events and on close, used only when it matches the log, schema and upcasters; otherwise full replay), `backups/<stamp>-<label>/`, and a `LOCK` (pid, host, boot minute, token). A torn last line is copied to `events.jsonl.torn-<stamp>` and cut; damage before the last line refuses to load. Exports are the event log plus metadata only; imports replay and re-check by append before writing to a new id, never overwriting. · Append-only log stays the source of truth; a crash or power loss never silently loses or invents data.
- D43 · 2026-10-21 · Secrets (GM key, GitHub token) never live in a campaign directory or the event log, so exports cannot carry them; the export format is an allowlist. · Simpler and safer than stripping secrets out of exports after the fact.
- D44 · 2026-10-21 · Every command produces exactly one event; a future command that emits several must add a group marker so torn-tail repair can drop an unfinished group. · A power cut mid-write would otherwise keep half a command.
- D45 · 2026-10-21 · Live protocol v2: clients send zod-checked `join` (player by character id; GM with key) and `command` frames; the hub runs commands through the engine's `execute` (authority there), persists via the store, then pushes the full state to GM sockets and only `projectForPlayer` views plus own-character notifications to player sockets. Raw events never leave the server. Notifications are level gains and free-point changes keyed by event seq; reconnect resends those after `lastSeq` (before the view), with `gap: true` when memory can't cover it. · One filtered path for every update keeps the canary guarantee simple.
- D46 · 2026-10-21 · Security model: GM key required for every GM action (WS join and `x-gm-key` on `/api`, deny-by-default on a normalized path); Origin must be same-origin; Host must be localhost, an IP literal or `*.local` (DNS rebinding). No TLS or failure throttle on the LAN: the default key is 256-bit random, and the GM window runs on the host over localhost so the key normally never crosses the network (it would if the GM used another device). GM_KEY comes from env (never a flag); otherwise generated and printed to the local terminal. · Proportionate for a home table while closing remote and browser-driven attacks.
- D47 · 2026-10-21 · Join helper ranks LAN IPv4 addresses 192.168/16 → 10/8 → 172.16/12 → other → CGNAT 100.64/10 → link-local; the best is the big URL and QR, every other address comes with its own QR. Interfaces are re-read per `/api/join` request. `/api/join` is GM-only (it reveals the host's interfaces; players already have the URL). QR is always black on white, error correction M, 4-module quiet zone, rendered by our own SVG code from the `qrcode` matrix. · A laptop often has Docker/VPN adapters; home wifi is almost always 192.168 or 10.x, and the GM can pick another if the guess is wrong.
- D48 · 2026-10-21 · The GM window gets the key in the URL fragment (`/gm#key=…`): browsers never send fragments to the server or in Referer; the page moves it to sessionStorage (this tab) and strips it from the address bar at once. The desktop app (MS.5) opens that URL; a terminal run prints `http://localhost:<port>/gm#key=…` only when it generated the key. · Keeps the key out of join URLs, QR codes, server logs and history while letting any browser on the host act as GM (MS.3).
- D49 · 2026-10-21 · GM broadcasts are a `system.broadcast` event (text ≤ 2000, recipients or null = everyone) kept in campaign state v3 as `broadcasts`; players get live per-recipient notifications plus a `messages` list in their view (only those addressed to them, never the recipient list). Recipients must exist, so undoing a recipient's creation is refused while the broadcast stands. Scheduling ("now or scheduled", M4.7) is not built yet. · DESIGN §7 makes broadcasts notable events; keeping them in state means a player who reconnects or a server restart never loses one.

M4.2 replaces this with the GM's class library. · ROADMAP MS.1 asks for one built-in starter class; the Archer kit matches the golden logs.
